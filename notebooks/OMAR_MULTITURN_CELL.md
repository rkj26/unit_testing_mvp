# Omar on the shared BigCodeBench notebook

Use `notebooks/results_bcbas.ipynb` with the team's Python 3.12 environment,
prepared from the authoritative `requirements.txt` before running any arms. An
already-compatible team environment can be used unchanged. Omar's detached workers
use the notebook's Python interpreter; notebook cells never run pip or install packages.

`requirements-omar.txt` is an **optional tested-version recipe**: the same
`-r requirements.txt` plus the locally tested `openai==2.45.0` / `httpx==0.28.1` pairing.
If deliberately choosing that recipe, use `python -m pip install -r requirements-omar.txt`
in the intended environment. This can change existing package versions, so it is not
an automatic second install before Omar. The tested pairing is not claimed to be the
only compatible configuration, and this file is not a complete global dependency lock.
The team's dependency files remain unchanged.

Working Docker and the reference arm's
sandbox image are required for fresh runs. Linux/WSL2 uses tmux; the Omar Windows
launcher is supported. A full-pool paid run is not validated by offline tests.
For a fresh **whole-team** Run All on Windows, use the team's Linux/WSL2
environment with tmux and Docker. Omar's Windows launcher does not port the other
team launchers or Linux-only native harness tests to Windows.

There are exactly **two Omar code cells**, generated by `notebooks/build_results.py`:

1. Initial, immediately after `ut_property.run()`: fresh Omar input generation and A.
2. Continuation, after the native shared coverage cell and before the plots:
   finish B/C/D, register all completed arms, then automatically compute the separate
   strict paired FPR/catch analysis in that same cell.

The notebook's `DATASET` is shared by **all team and Omar arms**, not an Omar-only
population selector. The current `data/bcbas.json` is present and unchanged:
453 tasks, 317 train / 136 test. Changing `DATASET` would change the population of the
entire comparison.
The runner loads this file and puts the relevant task and candidate code into
each model request. The model does not browse repository files automatically.

`archived/data/bcbas.json` serves only the original team's early
before/after comment comparison. It is **not an input to any model stage** and is
not a second experiment population. The committed scrubbed `DATASET` above remains
the experiment input. The BCB archived counterpart was recovered from the public
AttackSelection source, with equality checked against the entire current scrubbed
dataset document, not only task/candidate counts.
The source is `AttackSelection` revision
`1a0b4c6bf5a125a55b7512fb5ff910da437ad041`, using the existing
`scratch/convert_attackselection.py` converter and its strict population. The
restored archive's SHA-256 is
`14EF9D47F2F5BF362D8B7472878C44D0C4CC473A71A346C58935732D626D1563`.
The archive is ignored by Git, so a later reviewed handoff must explicitly include
that restored file in its file list; temporary public-source download caches do not

The shared `ut_property` is a settings reference, not A's saved suite or inputs.
Choose `OMAR_MODEL="terra"` (default) or `"deepseek"` once. All Omar model stages use
that selection; original team models, prompts, arm definitions, coverage and artifacts
are unchanged. A keeps the original `traceable_v1` prompt. B and C revise the same
frozen A source, differing in execution-feedback visibility; D only deletes existing tests.
No historical population, external input-review or expansion workflow is needed.

The initial cell defaults to:

```python
OMAR_MODEL = "terra"  # or "deepseek"
OMAR_ALLOW_PAID = False
OMAR_MAX_MODEL_CALLS = 0
```

It prints the whole-study upper logical model-call count **candidates × 5**:
fresh inputs + A + B + C + D. With the defaults, fresh paid work raises clearly,
so subsequent plots cannot silently omit Omar. A complete cached rerun is allowed
with zero allowance and makes no model or Docker calls. For a deliberately approved
fresh run, record a numerical prediction for C-versus-B, review provider pricing/quota,
then set `OMAR_ALLOW_PAID=True` and `OMAR_MAX_MODEL_CALLS` to at least the printed
whole-study count. This allowance is not a dollar cap or HTTP-attempt limit;
inherited retries may add provider attempts.

Run the initial cell, then the continuation when A finishes. The protocol launches
detached workers and the notebook follows completion; the kernel does not host
the paid run. Same model/run name resumes existing artifacts; choose a new suffix
for a fresh replicate. Switching model under the same name is refused.
On Windows, the new startup lock is OS-owned: an owning process's exit releases
the lock, so its persistent new-format guard file alone does not prevent recovery.
Do not delete that guard file; a live owner still blocks concurrent startup. An
unknown legacy guard still stops safely. Stop all launchers and verify that no
coordinator or worker owns the run before manually migrating a legacy guard;
never bypass it merely because the file looks old or a PID seems stale.

The other original team cells have their original launch behavior: Omar's paid
guard does not turn an uncached whole-team Run All into a no-spend operation.

The native plots retain their original whole-team semantics and use all registered
team/Omar arms. Native coverage can retain partial catches or mixed pass/property-error
records. The continuation also prints **Omar strict complete/error-free paired rates**
and saves schema 2 to `runs/<prefix>-coordinator/analysis-v2.json`. This separate analysis excludes
missing, failed, abstained, incomplete or execution-error grids, reports honest/attack
denominators separately, and bootstraps paired contrasts over task-ID clusters.
The primary held-out C-versus-B contrast uses **test tasks only**. Train rates,
contrasts, denominators and exclusions are reported separately as descriptive results;
there is no pooled train/test strict estimate. Failures without execution metadata are
counted with their saved blame/reason and excluded before any pair fields are accessed.
It uses 10,000 draws and seed 300; fewer than two eligible clusters gives no interval.
Task-cluster intervals are descriptive, not repeated-run uncertainty.
Native threshold/deployment figures and strict rates are **not interchangeable**.

`notebooks/OMAR_ANALYSIS_CELL.md` is the authoritative strict cell source:
the generator embeds its Python block into the continuation. Do not paste another
analysis cell or move its metric computation into a library. The strict analysis
makes zero model/Docker calls and never rewrites run records. Existing schema-1
`analysis.json` files are preserved. To update an old report, rerun the continuation on
the same completed cached arms; no new paid replicate is required. If a prior derived
`analysis-v2.json` differs, preserve that file under another name and recompute from
the same saved records.

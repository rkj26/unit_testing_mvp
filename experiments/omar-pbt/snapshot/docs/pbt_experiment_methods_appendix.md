# Property-based test experiment methods and results appendix

This appendix is a reproducibility ledger for the six completed studies indexed in [the experiment index](omar_pbt_experiment_index.md). It records the measured question, population, intervention, operational sequence, analysis entry point and principal result. It is intentionally an account of the completed artifacts, not a new claim that PBT establishes deployment safety. The reports and machine-readable artifacts linked below remain authoritative where a detail is study-specific.

## Shared measurement contract

The systems author property-based-style test functions for stored candidate programs, then execute those tests on a frozen set of candidate-specific inputs. In these studies, “property-based” means generated test functions evaluated over supplied input grids; it does not mean an open-ended Hypothesis fuzzing campaign. The initial authoring model is the Azure deployment `openai-api/azureai/gpt-5.6-terra` (short name `gpt-5.6-terra`), low reasoning, requested seed 300. A requested seed is not a guarantee of deterministic regeneration. The common authoring budget is ten requested tests and 8,192 output tokens; actual call/retry settings vary and are stated per study/report. The fresh controlled and BigCodeBench artifacts report snapshot `gpt-5.6-terra-2026-07-09`.

The original authoring protocol and its framing are implemented in [unit_testing.py](../pipeline/protocols/unit_testing.py); execution-informed revisions are in [test_repair.py](../pipeline/protocols/test_repair.py) and [second_revision.py](../pipeline/protocols/second_revision.py). The compared initial framings are separate files: [`framing_plain_v3.txt`](../prompts/framing_plain_v3.txt) and [`framing_traceable_v1.txt`](../prompts/framing_traceable_v1.txt). The latter adds a per-test traceability review (requirement, technique, oracle, validity, and value); it does not disclose the reference implementation or change the underlying test protocol. Revision templates are [`repair_tests_v1.txt`](../prompts/repair_tests_v1.txt) and [`second_revision_v1.txt`](../prompts/second_revision_v1.txt). The shared execution and data provenance machinery is in [sandbox.py](../pipeline/sandbox.py), [model.py](../pipeline/model.py), and [build_dataset.py](../build_dataset.py).

The candidate and its task statement, visible examples, invocation contract, and inputs are made available according to the relevant arm. Stored reference solutions and secret triggers are not supplied. `resolve='with'` allows the protocol to derive an oracle; it is not access to the stored reference solution. Dataset honest/attack labels are inherited from pool construction and were not independently re-established against every grading test. Inputs are targeted and statement-derived, not sampled from a deployment distribution.

A suite is counted as firing only when at least one assertion yields the sandbox outcome `catch`. Candidate crashes, property/test errors, parse failures, incomplete grids, abstentions, and infrastructure failures are not clean negatives. Each report specifies whether its primary denominator is protocol-successful, paired, or complete/error-free. In same-input honest-twin replay, an attack-authored suite is run unchanged on its paired honest implementation using the attack candidate's exact inputs. A per-test/input differential witness (attack catches, honest passes) differs from a whole-suite-clean differential (attack suite fires and the entire honest replay has no assertion catches); neither proves correctness outside the tested grid.

APPS execution used `python@sha256:78387bc3881b8273120a12ebe6c1ab22b018ccc2c9adf565ae1ac9b536e184ea` where documented. BigCodeBench used `omar-bcb-pbt@sha256:fd7deb31bc5174495c3cb9f25fcb503a900ea853740bb8d4fac1870265e31436` and a deepcopy harness. Sandbox limits were 120 seconds where documented. Trigger-search calls are separate from authoring/revision calls and use a 12,000-token output cap where stated. These settings must not be collapsed into one common call count or denominator.

## End-to-end workflow

The following sequence describes the common experimental spine. Per-study frozen plans and reports govern exceptions and exact eligibility; no step licenses rerunning a paid or candidate-execution stage during cached reproduction.

1. **Freeze the dataset and split.** Build or select the population under the study's recorded pool, source revision, seed, exclusions, and split. Store candidate labels as inherited pool metadata, not as newly certified ground truth. Record dataset and source hashes.
2. **Generate target inputs.** Run the separately named candidate-aware trigger-search stage when the study requires it. Treat trigger generation as a distinct model-call budget and artifact, not part of authoring.
3. **Review input domains.** Apply the statement-derived validator/review specified by that study. Preserve invalid/unresolved records and exclude only under frozen rules; never silently regenerate a favorable replacement. Freeze the retained inputs and their source-index mapping before authoring.
4. **Author suites.** Run the named `UnitTesting` prompt arm(s) on each eligible candidate. Reuse identical inputs across arms for each candidate. Keep raw responses, parsed suites, configs, usage and model/infrastructure failures.
5. **Execute the grid.** Run every parsed test on every retained input in the candidate's sandbox. Preserve per-pair outcomes, completeness, crashes, property errors, and infrastructure status. Only assertion `catch` is a firing event.
6. **Revise or select when specified.** For repair/revision studies, execute the original suite on its own candidate to produce bounded feedback; then call the revision arm(s) once under its frozen information contract and execute revised suites on the same candidate/inputs. For delete-only, validate that each retained function is byte-for-byte sourced from the original; preserve abstentions and source-ineligible records.
7. **Replay attack suites on honest twins.** Where included, run the attack-authored suite unchanged on the corresponding honest candidate with the attack input list. Cache identities and results separately; do not feed replay outcomes back to authoring or revision.
8. **Compute paired analysis.** Intersect eligibility separately for each contrast, report numerators/denominators and broad versus error-free sensitivity, and retain failures outside denominators as explicit exclusions. For task bootstrap, resample task clusters with both conditions/candidates together. Keep per-test/input witnesses separate from whole-suite-clean replay.

Study-specific deviations: studies 1–2 compare prompt framing and have no revision step; study 3 has a single feedback-informed training repair and no feedback-free revision control; study 4 freezes A/B/C where B and C each receive exactly one additional revision call per candidate, with the original chat history withheld and only C seeing bounded execution diagnostics (this is one revision round, not an iterative dialogue); study 5 applies that A/B/C structure to previously exposed BCB tasks with revision order alternated by candidate-index parity; study 6 adds a selector-only deletion arm, with abstention/source eligibility accounted separately. The delete-only selector implementation and prompt are embedded as `DELETE_ONLY_SOURCE` in the [delete-only generation notebook](../notebooks/azure_pbt_bcb_delete_only.ipynb); there is no separate `delete_only.py` protocol or external selector prompt file.

## Completed study ledger

### 1. Training prompt comparison — `plain_v3` vs `traceable_v1` (7 September)

**Question and design.** Exploratory training comparison of baseline prompt framing and traceability framing on 19 remaining APPS training tasks (38 honest/attack candidates), excluding previously inspected smoke task 3692. A separate trigger stage generated ten inputs per candidate; assistant-authored specification-domain review retained 379 inputs and excluded one invalid input. Both prompt arms used the same reviewed inputs for a given candidate. Candidate code was visible to both arms. Traceability asked for requirement, technique, oracle, validity, and value rationale; no critique, repair, or prompt tuning was included.

**Reproduction sequence.** Open [authoring notebook](../notebooks/azure_pbt_authoring.ipynb) from the repository root to inspect/freeze the input view and launch setup; its run prefix is `azure-terra-pbt-train19-s300-reviewed-v1`, with `-inputs`, `-plain-v3`, and `-traceable-v1` suffixes. The completed revision should not relaunch calls. For cached metrics and honest-twin replay, use [authoring replay notebook](../notebooks/azure_pbt_authoring_replay.ipynb), cells 1–6, with its launch/replay switches disabled. Primary JSON summaries and per-task replay records live under `runs/azure-terra-pbt-train19-s300-reviewed-v1-inputs/` and each arm's `same-input-honest-replay-v1/` directory.

**Result.** The broad paired, protocol-successful comparison had honest FPR 3/17 (17.65%) and attack firing 18/18 for both prompts. Under the stricter error-free paired sensitivity, honest firing was 1/14 (7.14%) in both arms. The preregistered 10-point FPR reduction target failed under both readings. Each arm retained a differential witness on all 17 replay-eligible tasks. Three traceability attack suites also fired on their honest twins, versus none for baseline; the traceability suites retained other differential witnesses. Traceability produced more exact duplicate test bodies. Full counts, exclusions, errors, hashes and interpretation are in the [verified report](azure_pbt_training_results_2026-09-07.md).

### 2. Frozen held-out prompt comparison — `plain_v3` vs `traceable_v1` (8 September)

**Question and design.** Frozen comparison on the original 30 APPS held-out tasks, after input-domain review left 29 tasks / 58 candidates and 576 valid inputs eligible. The 20 training tasks had been used for development; “held out” here means held out from this Azure prompt-development process, not necessarily never seen in any historical project experiment. Both arms received the same per-candidate reviewed inputs and visible candidate code; no critique, repair, input regeneration, or prompt tuning was added.

**Reproduction sequence.** The [launcher notebook](../notebooks/azure_pbt_heldout.ipynb) contains the frozen setup; the domain-screening record is in [domain review notebook](../notebooks/azure_pbt_heldout_domain_review.ipynb). Use run prefix `azure-terra-pbt-heldout30-s300-v1` and suffixes for reviewed inputs, `plain-v3`, and `traceable-v1`. For cached offline comparisons, bootstrap and replay, open [replay notebook](../notebooks/azure_pbt_heldout_replay.ipynb), cells 1–8, and keep launch/authoring switches disabled. The source records and summary JSONs are under corresponding `runs/azure-terra-pbt-heldout30-s300-v1-*` directories.

**Result.** Broad paired honest FPR changed from 4/29 (13.79%) to 3/29 (10.34%), a 3.45-point decrease, not the frozen ≥10-point target; broad matched attack firing was 22/28 (78.57%) in both arms. Under the stricter error-free paired sensitivity, honest FPR was 4/28 to 3/28 (14.29% to 10.71%), and attack firing was 21/25 in both arms. Exploratory paired task bootstrap 95% interval for the broad FPR difference was −17.24 to +10.34 pp, including zero. Replay witnesses were 21/25 vs 20/25. Reported deviations include one traceability syntax failure and one suite with 11 callable tests despite a ten-test request; these were exposed rather than silently repaired. See the [held-out report](azure_pbt_heldout_results_2026-09-08.md) for exact eligibility, replay contamination, token usage and sensitivities.

### 3. Exploratory execution-informed training repair (9 September)

**Question and design.** One execution-informed revision of the saved training `traceable_v1` suites on the same 19 previously inspected tasks / 38 candidates. The revision model received the original suite, task-visible information, fixed reviewed inputs and bounded diagnostics from executing that suite on its own candidate; it did not receive candidate source code, labels, honest twins, secret triggers, or replay results. This is development evidence on training tasks, not a held-out test.

**Reproduction sequence.** The [multi-turn notebook](../notebooks/azure_pbt_multiturn.ipynb) documents the repair configuration and launch switches; the run is `azure-terra-pbt-train19-s300-repair-v1`. Its cached analysis/replay cells can be run with `LAUNCH_*` and differential-replay switches false. The saved source arm remains `azure-terra-pbt-train19-s300-reviewed-v1-traceable-v1`; do not regenerate it. Prompt and implementation are versioned in `prompts/repair_tests_v1.txt` and `pipeline/protocols/test_repair.py`.

**Result.** On complete/error-free paired candidates, honest FPR decreased from 3/17 to 1/17 (−11.76 pp), while attack firing remained 18/18. The task-clustered 95% interval was [−29.41, 0.00] pp and included zero. Whole-suite-clean replay improved 14/17 to 16/17; pairwise witnesses remained 17/17. This exploratory point estimate did not resolve an effect. The [report](azure_pbt_multiturn_results_2026-09-09.md) records completeness, failures, duplicate suites and denominator rules.

### 4. Fresh controlled A/B/C second revision (14 September; report finalized 17 September)

**Question and design.** Does bounded own-candidate execution feedback improve revision beyond spending the same extra authoring call without runtime diagnostics? Thirty fresh APPS tasks (60 candidates) were sampled after exclusions and frozen. A authored initial traceability suites with visible candidate code. B revised those suites with code hidden and runtime outcomes withheld. C received the same revision contract as B plus bounded own-candidate execution outcomes. Inputs and initial suites were shared and frozen across arms. Primary contrast is C−B; A comparisons are secondary because call budget and information differ.

**Reproduction sequence.** The prospective details are in the [frozen plan](azure_pbt_multiturn_confirmatory_plan.md); launch/preparation and cached analysis are in [confirmatory notebook](../notebooks/azure_pbt_multiturn_confirmatory.ipynb). Study artifacts use `runs/azure-terra-pbt-fresh30-second-revision-s300-v1-study/`; associated source runs are baseline, `-no-feedback`, and `-feedback`. For cached reproduction, disable `PREPARE_DATA`, `FREEZE_REVISIONS`, every `LAUNCH_*`, and replay-launch switches; the notebook's primary, diversity and differential analyses read immutable records and caches. The versioned revision prompt is `prompts/second_revision_v1.txt`, implemented in `pipeline/protocols/second_revision.py`.

**Result.** On complete/error-free paired candidates, B→C honest FPR was 4/28 to 5/28 (+3.57 pp; interval [0,+11.12]); attack catches were 26/30 to 25/30 (−3.33 pp; interval [−10,0]). Thus the frozen feedback-improvement gate failed. Replay whole-suite-clean counts were 22/30 in both arms; pairwise witnesses were 24/30 vs 25/30. The result does not reproduce the earlier training point estimate, and does not establish that multi-turn testing generally fails. Full operational incidents and exclusions are detailed in the [confirmatory report](azure_pbt_multiturn_confirmatory_results_2026-09-14.md).

### 5. BigCodeBench A/B/C replication (18 September)

**Question and design.** Exploratory replication on 26 previously exposed BigCodeBench tasks / 52 candidates. A was the original candidate-visible baseline, B rewrote the suite without runtime feedback, and C rewrote with bounded own-candidate execution feedback. This was explicitly an all-evaluation derivative, not fresh held-out confirmation. All arms used the same reviewed candidate inputs. BigCodeBench used its pinned image and deepcopy harness. Revision call retries were disabled; execution feedback exposed bounded outcome counts/events, not candidate code, labels, or honest-twin outcomes. Revision order was alternated by candidate index: normal arm order for one parity and reversed order for the other, as implemented in the notebook worker.

**Reproduction sequence.** The [plan](azure_pbt_bcb_replication_plan.md) and [replication notebook](../notebooks/azure_pbt_bcb_replication.ipynb) contain preparation and launch details. Use run prefix `azure-terra-pbt-bcb26-s300-v1` and the `-baseline`, `-no-feedback`, and `-feedback` runs. Cached primary outputs are `primary-analysis-v2.json` and `primary-analysis-v3-supplement.json` under [study artifacts](../runs/azure-terra-pbt-bcb26-s300-v1-study/). For offline replay and analysis run [replay analysis notebook](../notebooks/azure_pbt_bcb_replay_analysis.ipynb) with launches disabled. Do not invoke launch functions to reproduce cached figures.

**Result.** On the common A/B/C subset, honest FPR was 2/22, 4/22, and 2/22 for A/B/C; attack catches were 21/21, 19/21, and 19/21. In the larger B/C-only subset, feedback reduced honest FPR 6/24 to 3/24, but the task-bootstrap interval was [−25, 0] pp and attack catches tied at 19/21. Feedback therefore did not beat baseline. Same-input replay and denominator details are in the [meeting report](omar_bcb_meeting_report.md).

### 6. BigCodeBench delete-only ablation (18 September)

**Question and design.** Could a selector reduce false positives by retaining only exact original test functions, without adding or rewriting code? The selector operated over the same exposed population and was constrained to return source-identical test-function selections. It is a deletion-policy ablation, not the replacement-suite A/B/C intervention. Of 51 parseable sources, 50 returned nonempty selections, one abstained, and one source was ineligible.

**Reproduction sequence.** The [delete-only plan](azure_pbt_bcb_delete_only_plan.md), [generation notebook](../notebooks/azure_pbt_bcb_delete_only.ipynb), [analysis notebook](../notebooks/azure_pbt_bcb_delete_analysis.ipynb), and [replay notebook](../notebooks/azure_pbt_bcb_delete_replay.ipynb) are the entry points. The run is `azure-terra-pbt-bcb26-s300-v1-delete-only`; cached analysis is under `runs/azure-terra-pbt-bcb26-s300-v1-study/delete-only-v1/`. Keep generation and replay launches disabled for no-API reproduction.

**Result.** There were 52 candidate records in the population. Of these, 51 source suites were parseable and entered selector handling: 50 yielded nonempty selections and one abstained. The remaining source (`BCB52_honest`) was source-ineligible and outside those 51. No matched honest-FPR reduction occurred: delete-only and feedback were 2/22 vs 2/22; delete-only and baseline were 3/23 vs 3/23. Attack catches were 17/20 vs feedback's 18/20, and 21/25 vs baseline's 24/25. The preregistered gate failed. Whole-suite-clean honest-twin replay was 16/20 for deletion, 17/20 feedback, and 19/20 baseline. Abstention is unavailable coverage, not a clean suite. See the [meeting report](omar_bcb_meeting_report.md) and [design assessment](omar_pbt_design_assessment.md).

## Reproduce cached analyses without paid calls

Use the repository's recorded environment/dependencies and start from the repository root, because the pipeline resolves datasets and `runs/` relative to the working directory. To reproduce results, open only the analysis/replay notebook listed above and run its cached-analysis cells with all preparation, launch, authoring, generation, Docker replay, and API-call switches disabled. Inspect the exact switch values first; notebook execution is not intrinsically read-only. In particular, do not call `Run.execute`, protocol `.run()`, launch helpers, trigger-generation functions, or replay functions that invoke `sandbox.run_raw`. BCB cached analysis commands are recorded in the [meeting report](omar_bcb_meeting_report.md). The training replay notebook was verified with sandbox execution replaced by a raising sentinel; fresh confirmatory cached analysis similarly patched API, network, process-launch, and sandbox boundaries to raise.

If required raw records or caches are absent, stop rather than reconstruct them by spending on model calls or executing candidate code. Some local runtime artifacts are gitignored; absence from a checkout is not evidence of a zero. Cached figures are reproducible from the retained data, but remote response regeneration is not promised to be bit-for-bit identical. Report hashes, exact run prefixes, eligibility, and failures from the per-study reports rather than combining denominators across studies.

## Cross-study interpretation and exclusions

The first two studies compare authoring prompt framing; studies 3–5 compare revision interventions; study 6 is a constrained deletion ablation. Their populations, prompt visibility, call budgets, input review, execution image, eligibility rules, and denominators differ. Training and BigCodeBench populations had prior exposure; only study 4 is the fresh controlled sample within this set. None independently validates benchmark labels against every hidden grader. Small task counts and task-cluster bootstrap intervals do not make inputs/tests independent. Any interval including zero is unresolved, not proof of no effect; identical observed attack outcomes do not prove equivalence. Raw attack catches should be read alongside same-input honest-twin checks. No results here establish selective-audit or deployment safety.
